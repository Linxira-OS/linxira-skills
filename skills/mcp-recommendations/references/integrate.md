# MCP 接入与信任边界

装好一个 MCP 之后，按下面顺序接入。每一步都要有可观察的证据，不要凭
「已安装」就假定可用。

## 1. 配置与重启

- 在宿主配置里注册服务器后重启/重载 MCP 客户端，让 `tools/list` 重新拉取。
- 记录落到哪份配置：项目级（如 `.mcp.json`、`.cursor/mcp.json`）还是用户级。
  project 级配置会随仓库分发，勿写入明文密钥。
- 密钥只放环境变量或宿主凭据存储，不要进仓库、日志、测试夹具。

## 2. 探测工具列表

- 连接后先枚举工具与资源，和预期对照：
  - 数量与名称是否符合该服务器的公开契约；
  - 是否拿到了 read-only 子集，还是全套写工具。
- 若枚举为空或连接失败，按服务器的健康检查定位：本地服务器看进程与端口，
  远程服务器看 URL、网络与鉴权。不要跳过直接调用。
- 记录工具清单快照，作为后续「行为变了」的比对基线。

## 3. 测试调用

- 先用最小只读调用验证：搜索、列目录、查询、获取上下文。
- 确认参数与返回结构，再进入写操作。
- 首次写操作前，与用户确认目标对象、影响范围与回滚方式。
- 写后读回核对：远端读回对象、本地读回文件，别只信返回值。

## 4. 与本地技能叠加

- 一个能力只由一个来源主导，避免重复：
  - MCP 负责取外部事实与执行外部动作；
  - 本地技能负责流程、规范、校验与交付格式。
- 顺序：本地技能决定「做什么、按什么标准」，MCP 提供「数据与动作」，
  本地校验技能负责「读回与判定完成」。
- 冲突时以用户明确要求为准；MCP 返回的字段名、枚举不要映射成本地技能的
  自定义术语，保留原文以便追溯。
- 有专用契约技能时，调用动作前先读该契约（如设计写入读 `open-design`）。
- 缓存与时效：远程文档、active 上下文、token 都可能过期；跨步骤使用前重新
  确认，不要把一次读取当作长期事实。

## 5. 信任边界

MCP 服务器是外部代码，可能把数据发往第三方，也可能修改本地/远端状态。接入
前明确：

- 身份：用个人账号、服务账号还是匿名？谁在授权？
- 数据出域：哪些内容会被发送，落到哪个主机/厂商？
- 写权限：能否改远端或本地状态？是否可缩小到只读？
- 成本：是否有配额、计费或速率限制？
- 供应链：仓库是否官方/活跃维护？锁到具体版本或镜像摘要了吗？

## 6. 最小权限

- 默认只读：先接 read-only 端点或子集，确需写时再放开。
- 缩小范围：限定 project/org/目录/文件根，而不是全账号或全盘。
- 分离身份：写操作与浏览/读取尽量用不同凭据。
- 可撤销：优先 OAuth 等可随时撤销的授权，避免长期 PAT。
- 记录：保留装了哪个服务器、什么权限、由谁批准，便于审计与善后。

## 完成标准

- 服务器已注册并重载，工具/资源清单已核对并留快照。
- 至少一次只读调用成功；写调用均已与用户确认并读回核对。
- 外部依赖（身份、数据出域、写权限、成本）已向用户说明。
- 与本地技能的主从关系明确，且未把一次读取当作长期事实。
